# 盲评：技能产出的方向是否比直接问模型更好

自动实测（`evals/`）只检查"守规矩"：三版都在、没改业务代码、没有替用户选定、品牌没被改。它不判断设计好坏。这份盲评回答的是：同一个任务，用 Variant Design 得到的三个方向，是否比直接让同一个模型"给三个方向"更值得比较、更值得继续做。

## 设计

- **任务：** `evals/fixtures/` 里的 pulse、harbor、bakery 和 ledger。每个都有原页面，任务就是 fixture 里的指令。
- **两组：**
  - **S 组**：装了技能的 agent，就是自动实测的产出。
  - **P 组**：同一个 agent、同一个模型、同一个项目，不装技能，直接让它"在 `variant-output/` 里给这个页面做三个不同方向 A/B/C 的完整页面，每个方向写一句它优化什么、放弃什么、适合什么场景，再推荐一个"。P 组的指令由 `evals/blind/package.mjs` 统一给出，不针对技能的长处改写。
- **呈现：** 每个任务给评审一份材料包，包括：
  - 原页面截图；
  - 两组各自三版的桌面和手机截图；
  - 两组各自的取舍说明和推荐。

  两组随机标成 X 和 Y，对照表另存，评审看不到。
- **评审：** 3–5 位做设计或产品的人，没有参与本项目。每人评全部任务，大约 30–40 分钟。

## 评分表（每组各填一份，1–5 分）

| 维度 | 1 分 | 5 分 |
|---|---|---|
| 区分度：三版是不是三种不同的思路 | 只是换了颜色或字体 | 布局、信息层级和交互都明显不同，各有立场 |
| 任务贴合：是否都在完成原页面的核心任务 | 丢功能、换内容，或者只是好看 | 同样的数据和功能，都更好地完成了任务 |
| 尊重现有品牌（pulse、ledger） | 改了品牌字体或颜色 | 品牌保持不变，只在结构和层级上发挥 |
| 说明与推荐：取舍说明和推荐有没有帮助决定 | 空话，或者和画面对不上 | 具体，能帮你判断选哪个、为什么 |
| 愿意继续：你会拿其中一版接着改吗 | 都不会 | 至少一版会，而且知道下一步改什么 |

最后问一题：**这个任务你更愿意拿哪一组继续做，X 还是 Y？为什么？**（必须选一个，理由一句话）

## 分析方式

- 先按任务、再按评审，汇总每个维度的分数和"更愿意用哪组"的次数，原样报告。
- 样本很小，不做显著性检验，不写"提升了 X%"。如果两组差别只在一两个人、一两个任务上，就写"没有看出明显差别"。
- 公开评审写的理由原文，比分数更有用。
- 结果记录到 `docs/research/YYYY-MM-DD-blind-review.md`。如果 P 组更好或者差不多，要照实写，并把具体原因作为改进技能的输入。

## 生成材料包

```sh
node evals/run.mjs --agent claude --no-skill --out <对照组目录>
PLAYWRIGHT_CHANNEL=chrome node evals/blind/pack.mjs --skill <技能组目录> --plain <对照组目录> --out <材料包目录>
```

把 `<材料包目录>` 整个发给评审（打开 `index.html`），连同上面的评分表。`<材料包目录>-key.json` 是 X/Y 的答案，评完再看。

## 已知偏差

- S 组的预览由技能生成，P 组的页面由模型自己写成静态 HTML，两组截图的取法相同，但页面的写法不完全一样。
- 每个任务每组只生成一次，结果有随机性。
- 评审知道这是在测一个"设计技能"，可能会倾向于认为写得更像设计说明的那组更好。所以材料包不提技能名称，说明文字只保留取舍和推荐，去掉格式标记。
