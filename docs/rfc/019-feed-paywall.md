# RFC-019 · 订阅源付费墙：把 feed 真的锁起来

- 状态：提案，待维护者决定第 7 节的六项；没有动手实现。
- 日期：2026-11-12。
- 关联：PRD-000（商业基线）、PRD-005（购买、权益与领取的实现决策）、RFC-006 §8.3（登录方式与支付供应商未定）、TODO 第 3 组「回访机制」和第 6 组 B5「隐私说明」。
- 起因：维护者 2026-11-11 提出「订阅 RSS 的部分可以加一个 paywall」，并在「公开摘要版 + 付费完整版」和「真的把 feed 锁起来」之间选了后者。本文写怎么锁、锁之前要先定什么、会碰到站上哪些既有承诺。

## 0. 结论

1. **锁法**：每个订阅者一条私有地址 `/feed/<令牌>.xml`，由 Vercel 函数校验令牌后返回完整订阅源；公开的 `feed.xml` 只剩一条说明项（「订阅源已改为付费，这里订阅」），所以旧订阅者在阅读器里看到一次说明，不是静默中断。网页不锁，搜索和 AI 搜索照旧能读。
2. **收款**：用支付供应商托管的结账页和 webhook，不自建卡处理，不做账号体系；凭支付时的邮箱领取和找回地址。这和 PRD-005 已写下的实现决策一致。
3. **顺序**：先量两三周需求（现在连有没有订阅者都不知道）→ 维护者定价格、收款主体、供应商、退款规则、条款和隐私说明 → 实现并在供应商测试模式下跑完整旅程 → 公告两周后切换。
4. **阻断项**：第 7 节的决定没有之前不能开工；其中收款主体和隐私说明两项不是代理能定的。

## 1. 现状（从代码核对，2026-11-12）

| 项目 | 现状 |
|---|---|
| 订阅源 | `website/scripts/prerender.mjs` 的 `rss()` 在构建时生成静态文件 `dist/feed.xml`：方向案例（`/d/<slug>`）和灵感条目（`/inspiration/<id>`）各一项，字段只有标题、链接、日期和我们自己写的一句中文研究要点；没有图片、视频和第三方文字；按日期倒序，全量（现在 169 条参考 + 5 个案例） |
| 入口 | 每个预渲染页的 `<link rel="alternate" type="application/rss+xml">`、页脚「订阅 RSS」、`llms.txt` 里一行 |
| 订阅者 | 数量未知。站点不收集任何数据（`docs/research/2026-11-08-analytics-state.md`），静态文件的请求也没有我们能查的日志 |
| 服务端 | 静态站 + 一个 Vercel 函数（`api/index.mjs` → `website/server/api-handler.mjs`，`maxDuration` 300），默认关闭模型路由。没有账号、支付、数据库或 KV |
| 价格页 | 本地版免费；Pro、Team 写明「尚未开放购买、开通或生成额度」，按钮打开 GitHub Issue；FAQ 第一条是「现在会扣款吗？不会」 |
| 既有承诺 | 灵感条目「仅链接」，不存第三方媒体（`docs/design-system.md` §8）；赞助页「不向赞助方提供读者的个人数据」；投稿页「展示方式与数据来源」一节写明数据从哪来 |
| 已有的规则 | PRD-005：服务端验签、通知幂等、不凭猜得到的订单号领取、只收履行购买所需的信息、撤销只影响后续领取、首期复用可靠支付和身份能力 |

## 2. 目标与不做

目标：

1. 没有令牌读不到条目。公开地址不再提供内容，但不中断：只剩说明项。
2. 付款后几分钟内拿到地址，不注册账号；地址丢了能找回；取消或退款后地址失效。
3. 所有阅读器都能用：令牌放在地址里，不用 HTTP 认证、cookie 或登录态。
4. 内容还是现在的生成方式：`rss()` 不变，锁加在分发层。
5. 不碰既有承诺：付费版仍只有链接和我们的笔记；订阅者的邮箱不给任何第三方；只收邮箱和供应商的订单号。

不做：

- 不做公开摘要版（维护者已否决；第 6 节记下它作为可回退的备选）。
- 不锁网页、不做全站付费墙，`sitemap.xml`、`llms.txt`、详情页都保持公开，所以 `docs/research/2026-11-02-geo-strategy.md` 的目标不受影响。
- 不做账号体系（TODO 第 4 组另议）、不自建支付、不自建发信。
- 不做每周邮件（TODO 第 3 组另议），本文只管 RSS。

## 3. 方案

### 3.1 地址与令牌

- 地址：`https://variantdesign.xyz/feed/<令牌>.xml`。令牌是 128 位随机值的 base64url（22 个字符），服务端只存它的哈希。付费播客和会员通讯普遍用「每人一条私有地址」（例如 Patreon 的会员 RSS），因为阅读器对认证的支持参差不齐，而地址谁都能粘贴。
- 校验：`vercel.json` 加一条 rewrite `/feed/:token.xml → /api/feed`；函数查到有效且未到期的令牌就返回完整订阅源，带 `ETag` 和 `Cache-Control: private, max-age=900`；不认识的令牌返回 404 和一行纯文本；已吊销的令牌在 30 天内返回只有一条说明项的订阅源（「地址已失效，这样找回或续订」），之后 404。
- 共享：技术上拦不住把地址转发给别人。对策是条款写明仅限个人，并按令牌记每日请求数和不同网络数（存 IP 的哈希，不存 IP）；超过阈值（草案：一天 20 个不同网络）自动换发令牌并发邮件通知本人。
- 完整订阅源怎么到函数手里：构建继续用 `rss()` 生成，但写到 `website/server/generated/feed-full.xml`（不在 `dist/` 下，任何静态路径都不能直接请求到），函数通过 `vercel.json` 的 `includeFiles` 带上它。这一点要在 Vercel 上实测，不行就改成函数在请求时从同一份数据生成。

### 3.2 内容

- 付费版 = 现在的 `feed.xml`，可以加英文笔记和「用在哪里」作为增量；仍然没有图片、视频，也不复制对方文字。付费改变的是我们笔记的分发方式，不改变条目的授权状态，投稿页「展示方式与数据来源」补一句说明。
- 公开的 `feed.xml`：只有一条项（标题「订阅源已改为付费」，描述一句话，链接 `/subscribe`），`<link rel="alternate">` 继续指向它。`llms.txt` 那一行改成同样的说明。

### 3.3 支付与领取（沿用 PRD-005 的实现决策）

- 结账：供应商托管的结账页或支付链接。候选是 Stripe Checkout；如果收款主体开不了 Stripe（Stripe 不面向中国大陆主体开户，以其公开的支持地区为准），改用 Lemon Squeezy 或 Paddle 这类代理商户，由它们处理税务，代价是抽成更高。供应商决定之前不写代码。
- 周期：按月或按年订阅、自动续费。这和 PRD-000「购买当前版本、不自动续费」的基线不同，因为订阅源是持续更新的内容；需要维护者确认。
- 领取：结账成功页带供应商的会话号回到 `/subscribe/done`，函数向供应商核实后显示地址并发邮件；邮件用供应商自带的收据模板，不行再接 Resend 一类发信服务。
- webhook：函数验签 → 按订单号幂等记录 → 生成令牌。取消订阅和退款的事件把令牌标为到期，当前周期结束后失效。重复、迟到、乱序的通知按 PRD-005 的规则处理。
- 找回：`/subscribe/recover` 输入邮箱，函数只发邮件、页面不显示任何东西，避免被用来探测谁订阅了。
- 存储：Vercel 市场里的 Upstash Redis（原 Vercel KV）或 Vercel Postgres；每条记录：订单号、供应商客户号、邮箱、令牌哈希、状态、到期日、创建和更新时间、最近 30 天的请求计数。不存卡信息，不存 IP 原文。

### 3.4 站上要改的东西

| 位置 | 改动 |
|---|---|
| `/subscribe`（新） | 价格、拿到什么、地址怎么加到常见阅读器、FAQ（能不能分享、怎么取消、退款规则、隐私） |
| `/subscribe/done`、`/subscribe/recover`（新） | 领取与找回 |
| `/pricing` | 加「订阅源」一栏；改掉「尚未开放购买」和 FAQ「现在会扣款吗？不会」 |
| 页脚 | 「订阅 RSS」改为「付费订阅源」，指向 `/subscribe` |
| `/submit`「展示方式与数据来源」 | 补一句：付费订阅源同样只含链接与我们的笔记 |
| `/sponsor` | 「不向赞助方提供读者的个人数据」已覆盖订阅者邮箱，不改措辞，但隐私说明要把订阅者数据列进去 |
| 隐私说明（新，B5） | 收集什么（邮箱、订单号、令牌的请求计数）、存多久、怎么删；措辞由维护者核对 |
| 服务条款与退款政策（新） | 代理起草，维护者核对；没有这两页不能开售 |
| `llms.txt`、`CHANGELOG.md`、`docs/design-system.md` | 说明项、网站包版本、新页面的组件行 |

### 3.5 先量需求

现在不知道有没有人订阅。锁之前先把 `feed.xml` 改走函数（内容不变），记两三周：

- 按 User-Agent 归类阅读器。Feedly、Inoreader 这类聚合器会在 UA 里报告订阅人数，可以直接读出来；桌面阅读器按不同网络数估。
- 只存 IP 的哈希和 UA，不存 IP 原文；记录写进 `docs/research/`，这也是 TODO 第 3 组「回访或订阅数」指标的基线。
- 要不要同时在 `/subscribe` 放「筹备中，留下邮箱」：这会开始收集邮箱，依赖 B5 隐私说明，由维护者定。

## 5. 风险

- **订阅者太少**：收入可能不抵供应商抽成和时间。P0 的数字决定要不要继续，这是量需求放在前面的原因。
- **地址被转发**：只能靠条款和异常计数，做不到技术上杜绝。
- **收款主体**：供应商能不能开户、税务怎么报，是维护者的事，也是最可能拖住整件事的一项。
- **口碑**：现有订阅者里会有人不满。说明项、两周公告期和「网页仍然公开」能减轻，但不能消除。
- **安全**：webhook 不验签会被伪造订单；找回页不限流会被用来探测邮箱。两项都在 P2 的测试里。
- **Vercel 细节**：`includeFiles`、rewrite 到函数的缓存行为、函数冷启动对阅读器超时的影响，都要实测，不能从文档推断。

## 6. 备选

- **公开摘要 + 付费全文**：公开 feed 保留标题和链接，付费版才有笔记。保留发现渠道、冲击最小，但维护者已否决；如果 P0 显示订阅者很多且多数不会付费，建议重新考虑。
- **托管会员平台**（Ghost、Buttondown、Substack 的付费订阅自带每人一条私有 RSS）：省掉函数、存储、支付和邮件的实现，缺点是每批内容要再发布一次、每月平台费、读者数据在别人手里，而且同样需要 Stripe 账号。如果 P1 定下来的收款通道只能走这些平台，就转这条路。
- **HTTP Basic 认证**：阅读器支持不一，手机阅读器尤其差，不选。

## 7. 待维护者决定

1. 收款主体和支付供应商（决定 Stripe 直连还是代理商户）。
2. 价格和周期（月、年；是否把英文笔记作为付费增量）。
3. 退款和取消规则；要不要团队多人令牌。
4. 隐私说明和服务条款：代理起草，维护者核对法律措辞。
5. P0 要不要做、做多久；切换前的公告期长度（草案两周）。
6. 存储用 Upstash Redis 还是 Vercel Postgres（代理可定，默认 Redis）。

定了 1–4 项再开 P2；P0 可以先做，它不依赖任何一项。
