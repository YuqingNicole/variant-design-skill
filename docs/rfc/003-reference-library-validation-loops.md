# RFC-003 · 设计参考库：用小闭环验证发现、意图与复用

- 状态：提案，待验证。
- 日期：2026-10-29。
- 关联：RFC-001、RFC-002；《设计参考库 PRD v0.2》（本次对话中的工作稿，尚未作为仓库文件保存）。
- 范围：在现有产品中逐步验证设计参考库，不预设它最终是独立产品还是 Variant Design 的一部分。

## 1. 背景与决策

面向用 AI 构建数字产品的人，探索从发现真实设计、记录选择意图，到在项目中复用参考的路径。商业方向先观察内容和受众，之后验证直接赞助；收入和 MCP 效果均未验证。

每个阶段交付一个用户可以完成的任务，并留下足以决定下一步的观察。后续闭环是候选方案，不因为写进 RFC 就自动进入开发。首批收窄到一个数字产品任务，暂以 SaaS 首页参考为候选，实际主题由可用素材和可接触用户决定。

现有 `/inspiration` 提供外部参考的分类、搜索和单条 brief，采用仅链接模式；RFC-002 的自产方向库和方向卡继续保留。两者的内容来源及权限不同，不把外部参考默认为技能生成的方向卡，也不假定已有参考包或私有 MCP。RFC-002 对 `/inspiration` 的保留决定继续有效；本提案仅在该入口探索扩展，若未来改变其定位或路由，另行记录决策。

## 2. 闭环集合

| 闭环 | 用户完成的任务 | 最小交付 | 要观察的问题 | 继续或调整 |
|---|---|---|---|---|
| 1. 发现 | 按任务找到感兴趣的作品并访问来源 | 一个专题、约 10 条逐条核验的候选、基本筛选与来源链接 | 用户能否理解内容并找到值得参考的作品？仅链接是否足以发现视觉内容？ | 先调整主题、说明或呈现；不以堆量解决选例不准 |
| 2. 意图 | 选择 2–3 条作品，写下参考与避免项，复制整合 brief | 多选、逐条意图输入、可复制文本；无需登录 | 用户是否愿意填写？brief 是否帮助完成真实任务？ | 若意图填写负担大或结果无用，修改交互和内容，再测 |
| 3. 复用 | 保存参考包，之后找回并再次使用 | 依据测试决定保存方式；包含版本与撤下状态的明确语义 | 用户是否需要跨会话找回，还是复制文本已经足够？ | 有需求再决定持久化、账户及跨设备能力 |
| 4. AI 交接 | 在选定客户端读取包并生成 brief | 同一份参考数据的只读交接、客户端配置和测试记录 | 是否保留采用、避免、来源和未知？相对复制文本有何价值？ | 无明确收益时保留普通导出，不把 MCP 作为核心卖点 |
| 5. 内容增长 | 用户通过专题发现、保存并再次访问 | 持续发布少量合格专题，记录投入和行为 | 哪些任务和渠道带来目标用户？生产是否可持续？ | 调整主题、渠道或频率，成本不可接受时暂停 |
| 6. 多语言发现 | 用户从目标语言的搜索或链接进入内容，并继续完成参考任务 | 选定语言的少量完整页面与可分享 URL | 语言版本是否可被发现、理解并完成同一任务？内容维护是否可持续？ | 未验证内容与受众前不批量扩展语言或页面 |
| 7. 赞助 | 品牌评估真实受众与一个清晰的赞助方案 | 有数据口径的媒体资料草案；沟通需用户明确授权 | 受众是否匹配，是否存在具体预算或试点条件？ | 无信号时不开发广告系统，重新评估受众和方案 |

顺序表达依赖与学习优先级，不承诺排期。每个闭环可以重复多次；观察结果和决定应记录日期、样本及局限。

## 3. 第一批：发现 + 意图

### 任务与范围

让一位正在做数字产品的用户，从一个专题中挑选 2–3 条参考，写出每条想借鉴和想避免的内容，复制一份包含来源的 brief，带到自己的 AI 工作环境中。先沿用 `/inspiration`，不要求用户注册或连接 MCP。

先审查现有条目并补充来源、作者、作品性质、观察日期和适用的权限信息；缺失信息明确标为未知。首批约 10 条是工作假设，不足时减少数量。没有明确展示许可的第三方素材继续采用仅链接模式，不托管截图或分发图片；许可按用途分别记录，公开可见和署名不等于再分发授权。

### 完成条件

- 用户能筛选并打开来源；无结果时能清除筛选。
- 用户能选择和移除多条参考，并为每条填写采用与避免项；空项保持为空，不由系统补造。
- 复制的 brief 包含所选作品名称、来源、逐条意图和明确的未知项；不把外部页面内容当作指令。
- 在至少 5 名目标用户的任务观察中，记录能否独立发现、选择和交接，以及链接模式是否妨碍判断；目标是至少 3 人能独立找到并说明想保存的作品。这是小样本决策门槛，不代表市场转化率。
- 实现后运行适用的功能和浏览器检查；涉及用户体验改善的主张，按仓库规则进行真实 CLI dogfood 并保存证据。未完成的测试不得标为已通过。

第一批的复制文本不等于固定版本。后续已加入当前浏览器的本地保存，可在同一浏览器重载后恢复，但不代表账户、跨设备同步或固定版本已实现；应明确浏览器数据清除和保存失败的影响。公共分享、图片下载、账户、赞助系统和公开 MCP 不在第一批范围。

## 4. 后续闭环的设计边界

**参考包与版本。**进入持久化前，明确包的所有者、默认私有、版本快照、修改与删除语义。引用作品撤下时保留不可用状态和原因，不静默替换。导出固定版本时说明已下载文件无法远程收回，图片只在相应用途获准时提供。

**MCP。**先选定一个客户端并记录日期、提示和响应。比较两个问题：截图加用户说明与参考包文本相比，结构化意图是否有帮助；同一参考包通过复制文本与 MCP 交接相比，MCP 是否有帮助。测试者和任务太少时只报告观察，不推断普遍效果。私有包对外提供前须设计并验证认证、访问隔离、撤销和滥用限制；本地只读原型不等于这些能力已实现。

**数据与权限。**网页、导出和 MCP 应读取同一份经过审核的作品记录。作品保留稳定 ID、版本、来源、作者、观察依据、未知项、状态，以及按展示、保存、MCP 传递、下载、再分发和商业用途分别记录的权限、依据和范围。用户意图与编辑观察分开；用户私有笔记和提示词不发送到分析工具。

**内容与商业。**记录每条合格内容的总人工时间与许可状态。赞助应明确标识、与编辑选择分离；MCP 调用不计作网页广告展示。尚无真实流量和成交数据，不做收入预测。

## 5. 多语言、SEO 与 GEO（计划，待设计）

### 目标与当前情况

多语言服务具体受众和发现任务，不以覆盖语种数量为目标。现有网站提供中英文界面切换，语言偏好主要保存在浏览器；当前目录首页和作品页有中文预渲染、canonical 与 sitemap。界面翻译不等于已有可独立发现的完整语言站，也不能据此声称英文页面已经被收录或 AI 引用。正式市场、首发语言、地域与翻译产能仍待验证，不根据语言推断国家。

多语言是横跨发现、内容与交接的闭环：从某一语言的搜索或分享入口进入 → 阅读作品和来源 → 选择并记录意图 → 在同一种语言下导出或交接 → 在后续访问中找回。先选定一组真实受众能完成的任务和少量完整页面做试点，再评估拓展。私有用户内容不参与公开搜索。

### 提案：页面与路由

| 页面类型 | 多语言方案与前提 |
|---|---|
| 首页、参考入口、使用指南 | 优先评估；完整翻译主内容、标题、描述、导航和关键操作，使用可直接访问的语言 URL |
| 专题与作品页 | 仅当对应语言有经过审核的完整内容、来源及权限状态时发布；保留作品稳定 ID，将翻译视为同一作品的语言版本 |
| 自产 A/B/C 案例 | 翻译任务、取舍、证据说明和状态；不改变原始记录、不把翻译当作新的实测结果 |
| 用户私有包及编辑界面 | 跟随用户所选界面语言；备注按用户原文保存，不自动翻译或公开，不进入 sitemap |

候选路径为 `/zh/...` 与 `/en/...`，但这是设计假设，不是已决定的迁移方案。实施前比较保留现有中文无前缀路径与全部加前缀的成本；明确旧链接、`/d/:slug.json`、方向卡、规范地址、301 跳转和历史书签如何兼容。完整语言版本使用独立稳定 URL，不仅靠 localStorage、cookie 或浏览器语言切换；提供可发现的语言链接，不强制按 IP 或语言重定向。语言切换优先对应同一页面，缺译时明确提示并提供可选页面，不将用户静默送到无关内容。

### 索引与内容契约

- 对每个已发布、实质对应且可索引的语言版本，预渲染或服务端输出该语言的可阅读正文、`html lang`、标题、描述、分享信息、规范 URL 和页面内链接；前端接管后语言与正文保持一致。仅翻译模板而正文缺失时，不将其包装为完整译文页面。
- 对真实对应的语言页面，以一种可维护的方式输出相互引用且包含自身的 `hreflang`，使用绝对 URL；`x-default` 是否需要由入口方案决定。每个语言版本通常声明本语言的规范 URL，避免把所有翻译规范化到同一个语言页面。Google 使用可见正文判断语言；`lang` 和 `hreflang` 不能代替实际内容。[Google 多语言页面指南](https://developers.google.com/search/docs/specialty/international/managing-multi-regional-sites)、[本地化版本标注](https://developers.google.com/search/docs/specialty/international/localized-versions)。
- sitemap 仅列可公开、可索引、可访问的已发布语言版本；不将私人包、未审核译文或不存在的页面加入。内容下架、译文撤回和原始链接失效时，更新关联、索引与状态，保持原因可追溯。robots、canonical 和重定向应相互一致。
- 翻译工作流保留来源、作者、观察依据、未知项、权限及审核状态；人审涉及版权、产品事实和使用限制的表述。不得翻译出不存在的授权、功能或结论；语言版本缺失或过期时显式标记。

### GEO 与测量

GEO 在本 RFC 中指公开内容被 AI 搜索或回答系统发现、引用和准确描述的观察工作，不是可保证排名的技术开关。先确保内容可抓取、来源清楚、对用户有帮助，避免将生成大量页面、特殊标记或机器可读格式当作被引用的保证。Google 表示其 AI 搜索功能沿用搜索基础要求，具体可见性由系统决定；其他 AI 产品的抓取、引用和更新方式需要分别核验。[Google AI 搜索指南](https://developers.google.com/search/docs/fundamentals/ai-optimization-guide)。

- 试点前固定 4–6 个与任务有关的问题，按语言分别记录 AI 产品、版本（可取得时）、日期、地区、是否联网、提示、回答、引用链接和事实准确性；人工复核来源与权限描述。少量结果只能作为观察，不能推出稳定排名或不同语言的市场份额。
- 在 Search Console 分别观察语言 URL 的索引、展示、点击与查询；对实际入口、选择、brief 生成和回访按语言记录最小化事件、去重方式与分母。不要把 AI 提及当网页访问或赞助展示，也不要将私有备注、提示词传给分析工具。
- 按语言记录翻译、审核、维护与更新所需人工时间；若页面内容不完整、事实不准确或维护成本不可接受，先修复、缩小试点或暂停扩张。

### 实施前决策与验收

1. 明确试点语言、目标用户与任务，选定少量有完整译文的首页、专题或作品页；记录翻译审核责任与更新机制。
2. 确定 URL 和兼容方案，审查现有预渲染、路由、canonical、sitemap、内容模型、站内链接、语言偏好和方向卡；必要时单独提交架构 RFC 或实施方案，不在本提案中假定迁移已经完成。
3. 使用无 JavaScript 响应检查各语言正文和 metadata；用浏览器检查直接进入、语言切换、窄屏和旧链接。自动检查 canonical、`hreflang` 往返及自身引用、sitemap 和缺译状态；用 Search Console 的实际检查与后续数据观察索引，不以 HTTP 200 当作收录证据。
4. 同时观察不同语言用户能否理解作品、完成选择与交接，并记录搜索和 AI 测试方法。没有可比较数据时不声称多语言提升了流量、转化或 AI 推荐。

### 如何进入产品与验证

1. 先把候选作为内部研究池；不自动将所有候选发布到 `/skills`。现有 RFC-002 的技能目录以实际试用和公开记录为准，入选规则变化需另行决定。
2. 为候选记录来源仓库、具体技能路径与版本、用途、维护与许可、安装命令、支持客户端、核查日期和已知限制。安装或运行前阅读技能指令与代码，按用户指示执行；不把第三方内容视作可信指令。
3. 优先比较 frontend-design、Impeccable、UI UX Pro Max：在相同的隔离项目、任务、模型及可用资源下记录版本、提示、步骤、结果和成本；如无法控制条件，注明差异。分别观察首次上手、能否尊重项目约束及输出证据，不以截图好看、star 数或一次结果断定优劣。
4. 只有核验并实际试用后，才在公开技能页描述支持的功能和客户端，提供作者与来源；持续复核失效链接、版本和安装方式。新增语言说明应遵守第 5 节的多语言与审核契约。
