# Version-bound delivery receipts · 2026-11-05

Branch `codex/delivery-receipts`, based on shared-dependency evidence head `4f597a0` (PR #160). Requirements: #19 complete integration inventory/receipts and #18 version-bound observations. Design: RFC-014. The broader backlog, full issue acceptance and prior human choices remain open.

## Implementation

New dependency-free `delivery-receipt.mjs` joins the real integration plan/backup, exact staging/target sets, source/constraint/shared-input fingerprints, verification references and optional current preview ownership. It seals exclusively under `.deliveries/` while integration is present. The inventory includes created/overwritten/unchanged paths and before/after hashes, not duplicate raw source or backup contents. Recovery is returned as argv/cwd without execution. It never selects, writes application files or creates observations.

Inventory validity and actual check status are separate. Missing reports stay unverified; wrong project/variant/version/target baselines and stale after reports refuse. Known non-target shared inputs must match the actual integration source. Real failed diagnostics remain failed; before/after reports can classify identical recorded prior failures. Preview conflicts cap verification at unverified. Read-only status recaptures inventory, reports, preview and checker identity; actual rollback retires current verification and later restored-target changes are distinguished. Cleanup preserves receipts/reports/backups. `.deliveries/` is excluded from source discovery and protected from preview ownership.

The evidence module exposes its existing read-only fingerprint; this is not another scanner or observation store. Bounds: 512 files/targets, 512 staging directories, 64 MiB total staging, 16 MiB per referenced file and 16 preview receipts. Invalid roots, symlinks/special files, hard links, corrupt backups and protected targets refuse before sealing. The receipt is local and unsigned; hashes do not authenticate observers or prove runtime-environment freshness. Primary design sources: [in-toto Statement](https://github.com/in-toto/attestation/blob/main/spec/v1/statement.md), [SLSA verification](https://slsa.dev/spec/v1.2/verifying-artifacts). Content binding and trust are distinct; no implementation of those formats or SLSA level is claimed.
