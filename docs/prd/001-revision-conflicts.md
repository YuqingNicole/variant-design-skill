# PRD-001 · 候选稿基准与修改冲突保护

跟踪 Issue：https://github.com/YuqingNicole/variant-design-skill/issues/17

- 优先级：P0；执行顺序：1；状态：待实现。
- 产品范围：安装到用户项目中的 skill 与文件历史 helper。
- 依赖：无；为 PRD-002、PRD-003 提供版本与内容身份。
- 证据基线：master `08d8623`，2026-10-07 临时目录复现。

## 问题

用户生成 B 的候选稿后，又修改了当前 B 的 hero。应用旧候选稿仍然成功，覆盖了用户的新内容。当前快照允许事后恢复，但在覆盖前没有报告候选稿已经过期。操作锁仅协调 helper 执行期间，不能覆盖候选稿生成期间或外部编辑器。

## 目标与解决方案

候选稿明确记录它基于哪个版本、哪些文件内容生成。应用前确认当前内容仍匹配；不匹配则保留当前项目和候选稿，说明冲突及恢复路径。编辑、选定和导出继续保持独立语义。

## 用户故事

1. 作为项目作者，我希望生成候选稿时记录基准，以便知道它基于哪次修改。
2. 作为项目作者，我希望手动修改被检测到，即使我没有更新版本号。
3. 作为项目作者，我希望旧候选稿被拒绝时当前文件保持原样。
4. 作为项目作者，我希望冲突信息指出涉及的文件，并告诉我如何重新生成或人工协调。
5. 作为项目作者，我希望候选稿和原有历史保留下来，避免重新开始。
6. 作为项目作者，我希望正常应用只推进 B，不改变 A、C 或最终选择。
7. 作为项目作者，我希望缺少基准的旧候选稿获得明确迁移提示，而非自动通过。
8. 作为项目作者，我希望多文件修改失败时不会被报告为成功。
9. 作为项目作者，我希望撤回仍能识别应用后发生的外部修改。

## 实现决策

- 在现有文件事务模块上加深，不替换已验证的快照、文件归属、路径保护和撤回机制。
- 在读取基准内容并开始生成候选稿之前建立基准记录；禁止在 apply 时补建记录以掩盖过期候选稿。
- 基准至少包括目标变体、基准版本、完整 owned-file 清单、文件内容指纹，以及会影响候选稿的 tokens、comparison、设计系统约束身份。选择状态不作为候选稿的内容冲突条件。
- 文件指纹识别绕过 helper 的编辑；文件集合新增、删除和内容变化都必须被检测。
- apply 取得现有操作锁后，先校验基准、完整候选稿、文件归属及区域限制，再快照与写入。任何预检失败不得改变当前文件、上下文或版本。
- 无基准或未知基准版本默认拒绝；迁移需从当前内容重新建立候选稿。保留旧历史的恢复路径，不提供默认强制覆盖。
- 不做自动合并。冲突后提供基准、当前稿和候选稿的比较线索，人工协调后基于新基准再次应用。
- helper 锁无法阻止外部程序在检查后写入；明确记录这一限制，不宣称跨编辑器的完全原子性。实现时评估提交前复检与失败恢复，不能仅凭版本号承诺解决所有并发。

## 验收清单

- [ ] R1：从基准生成 B 候选稿后手动修改 B hero；apply 拒绝，当前内容、上下文、版本和选定状态均不变。
- [ ] R2：两份同基准候选稿，第一份应用成功后第二份拒绝，即使变化都在允许区域内。
- [ ] R3：不更新版本号的外部文件编辑仍被检测。
- [ ] R4：文件新增、删除、tokens 或相关品牌约束改变时，返回有意义的冲突说明。
- [ ] R5：无冲突时 B 版本仅推进一次，A/C 不变，最终选择不变，快照可撤回。
- [ ] R6：无基准、损坏基准、非法路径及不完整候选稿均在写入前拒绝。
- [ ] R7：冲突不删除候选稿；输出重新生成/人工协调的可执行指引。
- [ ] R8：保留已有多次撤回、外部编辑保护、独占锁和恢复到新目录的回归结果。

## 测试决策

通过现有 apply/undo/恢复入口测试真实临时文件与上下文，不测试内部函数调用顺序。扩展已有文件历史测试，重点增加旧候选稿、双候选稿、同版本内容漂移和失败无写入场景；安装包解压后也运行一次基准保护。只记录已实际测试的中断恢复范围。

## 不在范围内

自动三方合并、协同编辑、通用项目导出、云数据库、界面改版、历史格式全量重写。

## 完成证据与跟进

关闭 Issue 前附实现 PR、回归命令与结果、冲突输出样例、正常应用与撤回记录、已知并发限制。PR 合并不自动等于所有验收项通过。本文是要求，当前代码尚未实现。
